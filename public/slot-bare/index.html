1b · Just <slot> inside <canvas>

No custom element, no library. A <slot name="…"> sits inside the canvas, and ordinary DOM with a matching slot="…" attribute is projected into it. The one requirement the platform imposes: slots only do anything inside a shadow tree, so the canvas has to be in a shadow root. Declarative shadow DOM makes that plain HTML.

slot="first"
I'm a normal child of a normal <div>.
slot="second"
<div id="host">
  <template shadowrootmode="open">
    <canvas content="drawable">
      <slot name="first"></slot>
      <slot name="second"></slot>
    </canvas>
  </template>

  <section slot="first"  drawable>…</section>
  <section slot="second" drawable>…</section>
</div>

<script>
  const canvas = host.shadowRoot.querySelector('canvas');
  const ctx = canvas.getContext('2d');
  canvas.onpaint = () => {
    ctx.reset();
    for (const slot of canvas.querySelectorAll('slot'))
      for (const el of slot.assignedElements())
        ctx.drawElementImage(el, x, y);   // wherever you like
  };
</script>

Page-level slots: a shadow root on <body>

Pushing it further: document.body can host a shadow root. Put the canvas and its named slots there, plus a default <slot> for everything else, and any top-level element on the page can opt in to the canvas just by adding slot="stage". The page's markup is otherwise untouched. Open it on its own.

Takeaways

  • Yes: a slot in a canvas reprojects normal DOM, and you only need a shadow root, not a custom element. With declarative shadow DOM the structure is pure HTML; the only script is the paint handler.
  • A <slot> in the light DOM does nothing. Outside a shadow tree it's an inert unknown-ish element, so <canvas><slot name="x"> in a normal document never picks up slot="x" content from elsewhere. This is the gap between the idea and the platform.
  • Projection is limited to the host's children. The body-shadow trick stretches "host" to the whole page, but only for top-level elements. A deeply nested element can't be slotted without moving it.
  • The slotted element needs drawable, or the slot needs a drawable wrapper around it in the shadow tree. Several elements can share one slot name and each is drawable on its own.
  • Slot fallback content draws too, so a canvas can ship default content that authors override by slotting.
  • What a native version might look like: if canvas children could reference elements by id (like popovertarget or aria-owns), you'd get reprojection of any element with no shadow root. Worth raising on the WICG repo.
