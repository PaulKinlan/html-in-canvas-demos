WebXR panels made of ordinary HTML

A form, a guest book, a diagnostics read-out and a keyboard, floating around you. Each one is plain HTML inside the <canvas>, uploaded as a texture on every paint. On this page you use them with the mouse or a finger. In a headset there is no mouse, so controller, hand and gaze rays are turned into pointer events on the same elements.

    How it is put together

    const surfaces = new HTMLSurfaces(renderer, camera, { scene });
surfaces.add(form, panelMesh);                  // texture + native hit testing on the page

// In a session the page has no pointer. Rays become pointer events on the same elements.
const pointer = surfaces.createRayPointer();
controller.addEventListener('selectstart', () => { pointer.move(raycaster); pointer.down(); });
controller.addEventListener('selectend',   () => { pointer.move(raycaster); pointer.up(); });

    Takeaways

    • The texture half carries straight over. A panel is a mesh with an element texture. Nothing about the upload changes when the same renderer is presenting to a headset.
    • The input half does not. Browser hit testing is tied to the page's 2D box, and an immersive session has no pointer over it. Rays have to be turned into events by hand, and synthetic events are untrusted: focus, caret placement, slider drags and <select> all need a hand-written stand-in.
    • elementFromPoint is the bridge. Lay the elements out flat with updateElementGeometry(), turn the ray's UV hit into a point in that layout, and the browser still answers which element is there, including inside scrollers.
    • A keyboard is just buttons. Keys that cancel mousedown never take focus, so setRangeText() plus an input event types into whatever field had the caret.
    • Whether paint keeps firing inside a real headset is the open question. The Diagnostics panel counts paint events during the session and falls back to forced uploads if they stop. The emulator cannot answer this, a device can.
