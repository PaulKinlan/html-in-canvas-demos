How it works

  • The document does not scroll. #sheet is a scrolling box as tall as the window below the menu bar, and it holds everything from the banner to the findings. The fx library wraps it in <fx-surface>, whose shadow root holds a canvas with content="drawable". The canvas is one screen in size whatever the length of the page.
  • The effect page-peel is one fragment shader. It gets the picture of the page and one point, the position of the paper's corner, from the CSS properties --fx-x and --fx-y. It rolls the paper round a cylinder that lies across the direction the corner has travelled, and draws the peeled paper mirrored and faded on top of the page. Where no paper is left it writes transparent pixels and a shadow.
  • The source layer is ordinary DOM under the canvas. It is seen through the transparent pixels.
  • Transparent pixels still take input. A clip-path polygon on the canvas host, computed in script from the same numbers as the shader, cuts the canvas along the roll. Taps, scrolling and text selection beyond it go to the source layer.
  • The paper lying on the page is pixels. The part of the page under it would take the tap. A handle element with the same outline lies over it and takes the drag instead. A round button on the paper's corner does the same job for a keyboard: Enter peels the page and puts it back, Escape puts it back.
  • "Sent by the server" is a second fetch() of this address with cache: 'no-store', read from response.body chunk by chunk. The first response, the one the parser read, cannot be read again from script. Its byte count is in performance.getEntriesByType('navigation') and is compared with the second.
  • "Live DOM" is document.documentElement.getHTML() with the shadow root of the canvas host passed in, written again at most four times a second while a MutationObserver reports changes. Lines that are equal at the start and at the end of the old and new text keep their elements. The lines between are replaced and marked.
  • The source layer is built in a shadow root that is not passed to getHTML(). So the live text does not contain the source view, and the observer on the document is not told about the view's own updates.

Findings

From Chromium 157 with software rendering, 412 px wide, on 2026-11-22. The rows above say what your browser does.

On this device: move the paper and scroll the page, and the number of frames the canvas drew is written here.

  • Works: one canvas draws a whole scrolling page. The page is a scrolling box inside the canvas. Scrolling it by touch, by wheel and from script raises a new frame, and elements are found at their scrolled positions. At 412 px wide and scale 2.625 the canvas is 2.24 megapixels and the page holds 28 MB of canvas memory in all, whatever the length of the page.
  • Works: a clip-path on the canvas host splits input along the roll. A shader can make pixels transparent but the element behind them still takes the tap. With the host clipped, elementFromPoint() gives the layer under the page, and a touch swipe there scrolls the source and not the page.
  • Works: both sources are the real ones. The second request returned the same number of bytes as the response the parser read (the navigation timing entry). The live text contains <fx-surface>, its canvas with content="drawable", and the --fx-x and --fx-y values, which change while the paper is dragged.
  • Works: a drawable canvas inside the drawn page. The inner canvas is in the outer picture and its button takes a tap. It needs contain: paint.
  • Works: the same picture on WebGL and WebGPU. Drawn into a texture with a software WebGPU adapter, the WGSL differs from the GLSL by 0.08 of 255 per channel on average.
  • Limit: the response that made the page cannot be read again. Script gets its size and timing, and can watch the parser add nodes, but the text has to come from a second request. If the server answers differently the second time, the tab shows the second answer. The page compares the byte counts and says when they differ.
  • Limit: the live text is attributes and text, not state. A typed value, a ticked checkbox, a scroll position and the pixels of a canvas are not in it. outerHTML also leaves out every shadow root. getHTML({ shadowRoots }) writes the ones it is given.
  • As built: setting textContent is reported as a change to the list of children. The clock replaces its text node each second, so the count of changes "to text" stays at 0 until the editable sentence is typed in.
  • As built: a view of the DOM that is in the DOM would show itself. The source layer is in a shadow root, which getHTML() skips unless asked and which a MutationObserver on the document does not report.
  • Not verified here: the WebGPU route on a screen, and how many frames a second a phone draws while the paper is dragged and while the page scrolls. The line above this list reports both on the device that opens the page. Also open on a phone: text selection handles in the source layer, the on-screen keyboard over a document that does not scroll, and how many chunks the deployed server sends (the test server sent one).
