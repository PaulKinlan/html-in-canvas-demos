EditContext and inline widgets

In Carets and highlights I left out a canvas-drawn editor using EditContext. I wanted to know if attaching new EditContext() to a drawable <canvas> can drive typing, selection and IME composition while native <input drawable>, <select drawable> and <button drawable> controls sit inline inside the code lines. How it works

Assigning canvas.editContext = new EditContext({ text, selectionStart, selectionEnd }) turns the focusable <canvas tabindex="0"> into an editable text host without a hidden <textarea>. Printable characters, Backspace, Delete and IME composition arrive as textupdate events on the EditContext, while textformatupdate gives underline ranges for active compositions. Navigation keys (arrows, Home, End) and Enter are handled in the canvas's keydown listener.

Inside the same <canvas content="drawable" layoutsubtree> sit four native HTML controls with the drawable attribute: a colour picker, a range slider, a <select> and a <button>. On each paint event, the canvas draws syntax-highlighted lines, the selection, IME underlines and the live wave strip at the bottom. Then it measures the width of each matching line and calls ctx.drawElementImage(el, x, y, el.offsetWidth, el.offsetHeight) to place each widget right after its literal.

Because Chromium hit-tests each drawable child where drawElementImage() placed it, clicking or tabbing into an inline widget hands focus to that HTML control instead of the canvas. The canvas's pointerdown and keydown listeners bail out whenever e.target !== canvas, so the widgets keep their native keyboard and pointer behaviour. When a widget changes, the script replaces the matching literal in the buffer and calls editContext.updateText() and editContext.updateSelection() so the browser's text model stays in sync.

Findings

Not yet run in headless Chromium 157 or on Android Chrome 159. Press the button under Live checks to test this browser.

  • Two text models share one canvas: attaching EditContext to the <canvas> handles text and IME for the canvas surface, while each drawable child control keeps its own native focus, pointer hit box and keyboard input.
  • Event guards are needed on the canvas: keydown and pointerdown bubble from drawable children to the parent <canvas>, so both handlers check e.target !== canvas before moving selection or calling preventDefault().
  • Tab order stays native: leaving Tab unhandled lets focus step from the <canvas tabindex="0"> through each drawn inline widget in DOM order. Any widget scrolled out of view gets inert = true so it doesn't remain an invisible Tab stop.
  • Moving widgets need a hit-test cache nudge: when typing pushes an inline widget right or down to a new coordinate, toggling a data-hit attribute on that element clears Chromium's cached hit box.
  • Not verified yet: real OS IME candidate window alignment (Japanese/Chinese/Korean desktop IME and Android Gboard composition), native <input type="color"> and <select> popups anchored to drawn coordinates, screen-reader announcements, and live check pass/fail in headless Chromium 157 and Android Chrome 159.
