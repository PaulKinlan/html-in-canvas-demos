Customisable <select> with a canvas-drawn picker

A select with appearance: base-select has a picker made of ordinary HTML. This page tests the two ways to combine that with HTML-in-canvas: a canvas inside the select that draws the options, and a select inside a canvas. Each select below is one <select> element with real <option> children. Open them with a tap, a click or the keyboard.

Show the code a picker drawn by a canvas
  1. Write an ordinary select and add picker="…". The options are filled in by the page script here; they can equally be written in the HTML. The form reads the values as usual.
  2. Load the library. The rest of the page script fills in options and prints the form's values.
  3. Inside the library: move the options into a drawable canvas inside the select. A select collects options from all its descendants, so they remain its options.
  4. A layout is a function from an option's index to a matrix. This is the wheel. The fisheye, radial and carousel layouts have the same shape.
  5. The 2D route: one drawElementImage() per option. The call draws the option and moves its hit box to the same place, so the browser's own click, hover and focus handling choose options.
  6. The first paint event is the "picker opened" signal. A select fires no event when its picker opens.
  7. The carousel layout returns a matrix with perspective.
  8. The WebGL route: each option is a texture, uploaded with texElementSubImage2D().
  9. After a GPU frame, updateElementGeometry() gives each option its hit box, using the same matrix as the shader.
  10. The WebGPU route uploads with drawElementImageToTexture().
  11. Choosing and closing from script. There is no hidePicker(), so an empty popover is shown to close the picker.
  12. The options are styled with CSS.
  13. The whole library.
<script type="module" src="/lib/select-picker.js"></script>

<select name="time" picker="wheel">
  <option>09:00</option>
  <option>09:30</option>
</select>

A canvas inside each option

The card is a form drawn into a canvas with a 2D filter. The select next to it chooses the filter. Each option holds a small canvas that shows the card as it is now with that option's filter applied, so the previews keep the clock's current time and whatever is typed in the field. The button shows the chosen option through <selectedcontent>, which clones the option's canvas element without its pixels, so the page draws the clone as well.

Findings

  • Options can live in a canvas inside the select. With appearance: base-select, <select><canvas content="drawable"><option drawable> parses, select.options finds the options, and the canvas draws each one wherever it likes. Click, hover, :checked, arrow keys, typeahead, Enter and Escape are still the select's own. The four pickers above add no keyboard code.
  • Hit testing follows the drawing. In a 2D canvas, drawElementImage() under a transform moves the option's hit box with it. With WebGL or WebGPU, updateElementGeometry() accepts the carousel's perspective matrix. Where two options overlap, the one drawn last gets the click. z-index on the options does not change that.
  • An option that is not drawn keeps its last hit box. The library moves options that are off the wheel or carousel far outside the canvas. They stay reachable with the arrow keys, and the layout turns to the focused option.
  • The select fires no event when its picker opens. No toggle or beforetoggle reached the select in Chromium 157. The canvas's first paint event is the earliest signal. Before that the options have no paint record and drawing them throws.
  • There is no hidePicker(). blur(), a synthetic Escape key, option.click() and toggling disabled or inert all leave the picker open. Showing an empty popover="auto" element closes it, because the picker is in the same stack. The fisheye and radial pickers use that after a slide-and-lift gesture, because a touch that moved sends no click. Setting appearance: auto for one style recalculation also closes the picker, but if the mouse is over the picker at that moment the select's computed appearance stays auto afterwards and it becomes the browser's own select.
  • A press chooses on mouseup, not on click. A mouse drag that ends over an option chooses it. The library captures the pointer on the canvas once a drag passes 7 px, so the release goes to the canvas.
  • touch-action: none did not stop the page panning. With touch emulation, a vertical drag on the wheel scrolled the page and cancelled the pointer, with touch-action: none on the canvas and on the options. The library cancels touchmove inside the picker instead.
  • One tap opens one picker. showPicker() needs user activation and uses it up, and synthetic clicks and keys do not open a picker. The live checks below therefore share a single test select.
  • A canvas in the button can draw <selectedcontent>. With <button><canvas><selectedcontent drawable> the browser still fills in the chosen option on every change, and the canvas draws it. The hand of cards and the helix above keep the pixels of the old value and roll the new one in.
  • A canvas inside an option works, with two limits. It can draw its own drawable children once the picker is open (while closed there is no paint record). <selectedcontent> clones the canvas element on every change, and the clone has no pixels and no paint handler.
  • A select in a canvas keeps its picker out of the canvas. The picker is top-layer content. It is not in the picture drawElementImage(select) draws, and the outer canvas cannot draw an option of the open picker either ("No cached paint record"). It opens upright next to the bounding box of the drawn button, whatever transform the button was drawn with. To transform the picker too, put a canvas inside the select as above.
  • The picker cannot animate out. When the select closes, the options stop painting in the same frame, so the canvas has nothing to draw a closing animation with. The opening animation runs because the picker is already open.
  • Not verified on real hardware. These results are from Chromium 157 with software rendering, driven by Playwright with mouse and emulated touch. The WebGPU route was checked by rendering to a texture and reading it back, not by showing it. Touch dragging inside the picker on Android Chrome has not been tried on a device.

More select modes to try

  • A lens over a long list. Draw the whole list small and put a magnifying shader under the finger, using the lens code from /lens/. The fisheye list above does this with per-option transforms. A shader could bend the text continuously.
  • Options as physical objects. Options hang on springs or fall into a pile, using the mesh hit testing from /physical/. Shake the phone to shuffle. It answers whether a choice can be made by throwing an option at a target.
  • A map or seat plan as the picker. Each option is drawn at a position on an image: seats in a theatre, pins on a map, keys on a piano. The select keeps the value and the keyboard order.
  • A colour select that samples its own pixels. Options are drawn over a gradient, and the picker reads the canvas back to offer the colour under the pointer as a new option.
  • A multi-select that shows its history. Keep an ElementImage of the picker at each change and let the person scrub back, as on /time-scrubber/.
  • A picker shared with another screen. Stream the picker canvas to a phone as on /remote/, so a select on a television is operated from the phone with the phone's own touch gestures.
  • A transition from the option to the button. The chosen card flies from the picker into the button. This needs the option to keep painting after the picker closes, which it does not today. A copy of its pixels taken on the last frame would work.
  • <select multiple>. A list box is in the page, not the top layer, so a canvas could draw it without any picker.
  • Other controls. /datalist/ draws the suggestions of <input list> with a canvas, and /inputs/ does the same for date, time and colour pickers.
