      How it travels

      1. Capture. The panel sits in a <live-region>, whose shadow root paints it through an HTML-in-canvas canvas. Every paint copies the result to a second canvas, and captureStream() turns that into a video track. No screen-capture prompt, and nothing outside the element is in the picture.
      2. Introduce. Both ends open a WebSocket to a room on the Worker (a Durable Object), which relays the WebRTC offer, answer and ICE candidates.
      3. Stream. Video goes peer to peer. Input comes back on an RTCDataChannel as normalised coordinates and keys, and is replayed on the real DOM.
      4. Fall back. If the peers can't connect, the phone asks for relayed frames instead: JPEGs sent through the same WebSocket at a few frames a second.

      Takeaways

      • Only the source needs HTML-in-canvas. The viewer is a <video> and a few event listeners, so it runs on any phone.
      • Controls that open native UI need help. A <select> popup or an on-screen keyboard belongs to the device in your hand, not the source. The source sends the options and the viewer shows its own native picker; a map of the element's fields tells the viewer when to raise its keyboard.
      • The element map is the part pixels can't carry. Alongside video the source sends roles, names and positions of the interactive elements, read from the real DOM. That is enough to rebuild an accessible outline at the far end.
      • The source tab must stay visible. A hidden tab stops painting, so the stream freezes. The viewer is told and says so.
      • Without a TURN server some networks won't connect. That is what the relay fallback is for. It costs one Durable Object message per frame.
