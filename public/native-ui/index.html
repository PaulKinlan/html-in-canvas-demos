DOM elements inside egui and Qt Quick apps

egui (Rust) and Qt Quick (C++) are native UI toolkits. Compiled to WebAssembly they draw every widget themselves into one WebGL canvas, so the page has no real inputs. Here both apps contain real <input>, <select> and <textarea> elements. The toolkit lays them out and draws them from a texture filled by texElementSubImage2D(). The browser handles their input.

Qt Quick

Qt 6.10 for WebAssembly, with Qt Quick Controls. It is not loaded until you ask.

The email, plan and notes fields are DOM elements shown by a DomItem in the QML scene. The sliders are Qt Quick Controls that set the items' opacity and rotation, and the rotated field still takes clicks and typing where it is drawn.

Findings

  • Both toolkits took a DOM element as a widget without changes to the toolkit. egui needs a paint callback (egui_glow::CallbackFn). Qt Quick needs a QQuickItem whose node wraps a GL texture (QSGOpenGLTexture::fromNative()). Each bridge is about 200 lines.
  • The element is drawn by the toolkit, so it is in the toolkit's z-order. An egui window covers the DOM fields, an egui scroll area clips them, and Qt Quick rotates and fades them. Toolkits that put HTML over or under the canvas cannot do this.
  • Layout goes both ways. The toolkit sets the element's width, the browser lays it out, and the toolkit reads offsetHeight to size its widget. The paragraph of DOM text wraps to the width egui gives it.
  • The browser does not know what the toolkit draws on top. An element is hit tested wherever its geometry is. The egui bridge asks egui (Context::layer_id_at()) in a capture-phase listener before an event reaches an element, and moves the element's geometry off the canvas when an egui window is over it at the pointer. The Qt proof does not do this yet.
  • Two things on the page want each event. egui listens on the canvas and Qt on its window element, and an event on a child element bubbles to both. The bridges stop propagation at the element. egui already ignores pointer moves when elementFromPoint() is not its canvas, which helped.
  • Focus is split. Tab moves between the DOM fields in DOM order and between toolkit widgets in the toolkit's order, and the two orders are not joined. A click hands focus over correctly in both directions.
  • The texture must be premultiplied. egui and Qt Quick both blend premultiplied alpha. Without UNPACK_PREMULTIPLY_ALPHA_WEBGL text on a transparent background is drawn too heavy.
  • Qt's canvas is in a shadow root and Qt creates it. The element has to be moved in after Qt has a GL context, and it needs inline styles. Setting content="drawable" on a canvas that already has a WebGL context works.
  • Raw GL inside Qt Quick's frame prints warnings. Chromium logs five texParameter: no texture bound warnings per item at start-up, from Qt's renderer after the foreign texture is wrapped. The textures are drawn correctly. Not investigated further.
  • Some of what the browser paints for a field is left out of the texture. The explainer excludes spelling and grammar markers, pending autofill previews, IME pop-ups and IME composition formatting from element images for privacy. The textarea has spellcheck on and a misspelt word, and no marker is drawn.
  • updateElementGeometry() does not drop cached hit-test results. In Chromium 157, elementFromPoint() at a point that was hit tested just before the call keeps returning the old element, while a point two pixels away is correct. Any DOM mutation clears it, so both bridges toggle an attribute on the canvas after each geometry update.
  • eframe focuses its hidden text input when it starts. The page makes focus() a no-op while the app starts so that opening the page does not move focus.
  • Not verified on a phone. Both apps were tested in headless Chromium 157 at a 2.625 device scale with touch events. DevTools device emulation gives egui a wrong scale (it reads a canvas size that is not in device pixels), so use a real phone. Touch-dragging on a DOM field does not scroll the egui scroll area under it.
