View Transitions API with HTML-in-canvas

Four experiments with document.startViewTransition(), view-transition-name, element.startViewTransition() and cross-document transitions, each with a <canvas layoutsubtree> in the page. The live transitions page does not use this API. This page does.

  2. The names. The canvas is a replaced element, so it can carry a view-transition-name like an image can.

  • Name on the canvas: works. The old snapshot contains the card as the canvas drew it. The new snapshot is live: the clock in the card keeps counting while the canvas moves and changes size. The canvas gets paint events during the transition.
  • Name on the card: the group moves, the picture is empty. Chromium makes ::view-transition-group(the-card) and animates it between the two places drawElementImage() put the card, but both snapshots are blank. The card only shows inside the canvas cross-fade.
  • Started on the grid element: works, the same as on the document, and the rest of the page stays interactive.
  • Started on the canvas element: the canvas is blank for the length of the transition. The promise resolves and the pseudo-elements exist, but nothing is drawn where the canvas is.
  • Started on a child of the canvas: the tab crashes. This is on its own page so that it cannot take this one down.

Findings

  • A drawable canvas takes part in a view transition as one picture. Its snapshot is the canvas bitmap, HTML children included. The new snapshot is live, so the canvas can keep animating under ::view-transition-new().
  • A canvas child cannot be its own transition element. It gets a group with the right box and no picture. To move one element on its own, give it its own canvas and name that canvas.
  • The old and new snapshots cannot be read from script. There is no call that hands ::view-transition-old() to a canvas or a shader. A shader transition has to keep both states itself (two live elements, or an ElementImage taken before the change) and switch the cross-fade off.
  • Work that waits for a paint event must be done before startViewTransition(). The canvas gets no paint event while the update callback is pending.
  • Element-scoped transitions and drawable canvases do not mix yet. On an ancestor of the canvas they work. On the canvas they blank it. On a child of the canvas they crash the renderer in Chromium 157.
  • Between documents, a named canvas cross-fades like any other element. An ElementImage cannot follow the navigation, so a shader between two documents needs pixels: the old page stores a picture of its canvas, and the new page draws from that picture to its live content.

Not tried yet

  • Use ::view-transition-group() of a canvas child as a timing source: it has the right box at every moment, so the canvas could read it each frame and draw the child there itself.
  • Navigation API navigate with intercept() and a shader transition for a single-page app's route changes.
  • view-transition-class and nested groups (view-transition-group: contain) with one canvas per list item.
  • A page-wide shader: put the whole page in one canvas, so that a transition between any two states is drawn by the canvas and the View Transitions API is only used for timing.
