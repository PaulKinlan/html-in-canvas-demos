Newer WebGPU features on element textures

A small form and a block of text are uploaded to WebGPU textures with drawElementImageToTexture() and drawn in five tiles. Each tile uses one WebGPU feature that is newer than the first WebGPU release, when the device has it. When the device does not, the tile draws the same picture another way. Live checks

ResultExperimentDetail

Findings

  • An element texture works with all five features. drawElementImageToTexture() fills an ordinary rgba8unorm texture, so a swizzled view of it, a float target fed from it and a dual-source blend over it need nothing special.
  • A swizzled view needs its own usage. The element texture must have RENDER_ATTACHMENT for the upload. The swizzled view is made with usage: TEXTURE_BINDING so it is not also a render target.
  • Immediates replace a buffer and a bind group. var<immediate> p: P; in the shader, immediateSize on the pipeline layout and pass.setImmediates(0, floats) before each draw. The limit is maxImmediateSize, 64 bytes in Chromium 157. The other way here is one uniform buffer with a 256-byte slot for each draw and a dynamic offset.
  • An 8-bit trail never fades out. Multiplying an 8-bit value by 0.95 and rounding stops near 10 out of 255, so old trails stay as a mark: after 200 fades the rgba8unorm trail is still 14 of 255 brighter than the background, and the float ones are at 0. Eight additions of the form read 251 of 255 from a float target and 201 from the 8-bit one, which stops at 1.0. rgba16float blends on every core device; rgba32float needs float32-blendable and cannot be sampled with a filtering sampler, so the shader reads it with textureLoad().
  • primitive_index is a fragment shader input only. Moving the shards apart happens in the vertex shader, which has to work the triangle out from vertex_index / 3 anyway. For a list of separate triangles a flat varying carries the same number to the fragment shader, so the feature saves one varying here. It is needed when triangles share vertices through an index buffer.
  • Subpixel text needs the canvas to match the screen's pixels. The canvas is sized from devicePixelContentBoxSize, and the text element is laid out at three times its shown size so each canvas pixel has 3 × 3 texels. The order red, green, blue is assumed. Most phone screens do not have that layout, so there the per-channel coverage shows as coloured edges and plain alpha is the better choice.
  • A compatibility mode device runs every shader on this page. On the software adapter these pages are tested with, requestAdapter({ featureLevel: 'compatibility' }) gives a device with lower limits (4096 pixel textures, 4 colour attachments) that still has swizzle, immediates and float blending, and its picture matches the core one. Flat varyings are written @interpolate(flat, either), which compatibility mode requires.
  • Not confirmed here. That software adapter has no dual-source-blending and no primitive-index, so those two shaders have never been compiled in testing, and it cannot show a WebGPU canvas on screen. Both need a real GPU. The live checks compare each feature with its other way on the device they run on.
