Shader uniforms written in CSS only

Twelve cards are drawn by one WebGL canvas through one fragment shader. The shader's uniforms are CSS custom properties: uniform float uWave reads --u-wave from each card. Each card carries the CSS rule that sets its uniforms, in a <style> element that is displayed on the card. The rules use transitions, keyframes, typed attr(), sibling-index(), random(), if(), style queries, progress(), @function and a view timeline. No card has script of its own.   3. The fragment shader. Every float and vec4 uniform it declares becomes a custom property.
  4. The binding. Parse the declarations, register the properties, read computed values, set the uniforms.
  5. Once a frame. Read every card's values and ask for a paint only when one changed.
  6. On paint. Upload the cards whose picture changed and draw each with its own values.

How it works

lib/css-uniforms.js reads the shader source, finds each uniform float and uniform vec4, and registers a custom property for it with CSS.registerProperty(): a <number> for a float, a <color> for a vec4. A registered property has a type, so the browser can interpolate it in a transition, an animation or a scroll timeline. Each card is a drawable element with its own texture. For each card the page reads the computed values with getComputedStyle() and sets them as uniforms before drawing that card's quad.

A change to a custom property does not change the card's picture, so the browser raises no paint event for it. The page reads all values once per animation frame while the canvas is on screen, compares the strings with the previous frame, and calls requestPaint() only when one differs. The line under the canvas shows what that read costs.

The rules on the cards are live <style> elements with display: block and contenteditable. Editing one changes the page's style sheet, and the next frame's read picks up the new value.

Findings

  • In Chromium 157 every CSS feature on the cards produced a number or a colour that getComputedStyle() returns resolved: typed attr(), sibling-index(), random(), if() with style(), a style range query, progress(), @function, and values in the middle of a transition, an animation or a view timeline.
  • Changing only a custom property raises no paint event, also when the property is registered and animating. The canvas has to poll. Reading 12 properties on 12 cards, with animations running on all of them, took about 0.9 ms per frame in the test browser, which includes resolving the animated values.
  • A registered <color> property in a transition is returned as rgb() or rgba() with interpolated components, so a colour uniform can be animated by CSS.
  • random() keeps its value for an element across reads, so a seed does not flicker. It changes on reload.
  • A <style> element with display: block inside a drawn element is part of its picture, can be edited there with contenteditable, and its rules apply while it is edited.
  • A view timeline on a drawn card runs from the card's layout position in the page, so a card can form as it scrolls into the window.
  • Not verified: Chrome 159 on the test phone, and the cost of the per-frame read there. The status line reports it.
