Paint clocks

Four ideas from the element catalogue. Some elements repaint by themselves: an indeterminate progress bar, a blinking caret, a playing video, an animated image. Each repaint raises paint on the canvas that holds the element. On this page that event is the only clock. No demo calls requestAnimationFrame(), starts a timer or asks for paints in a loop, so each effect runs at the rate of its element and stops when the element stops. The line under each canvas counts the paint events.

How it works

A drawable canvas gets a paint event when the picture of one of its drawable descendants changes. An element that animates by itself therefore raises a steady run of paint events, at its own rate, for as long as it animates. Each demo has one paint handler and nothing else that runs over time:

  • Where the time comes from. The loading effect reads performance.now() inside the handler, so it moves at the right speed at any paint rate. The film reads video.currentTime. The flag and the heartbeat count paint events, so their speed is the element's rate.
  • Stopping. There is nothing to stop. When the bar gets a value, the field loses focus, the video pauses or the image is removed, the element stops repainting and the handler is not called again.
  • The clock does not have to be drawn. A drawable element raises paint whether or not the handler draws it. It does have to be painted by the browser at least once: an image that has opacity: 0 from the start raised no events, and an element with visibility: hidden has no picture. An image that was already running kept raising events after it was given opacity: 0.
  • One exception. An element has no picture until the browser has painted it once. If a draw fails for that reason, the handler asks for one more paint, at most 30 times, when the page starts.

Live checks

The checks wait for a tap and take about 25 seconds, because each one counts paint events for a second or more. Each builds its own small canvas in a corner of the window, and none of them touches the demos above. The caret is not checked here, because a check must not move focus: its rate is printed under the heartbeat demo.

Findings

Measured in headless Chromium 157 on 2026-11-21. Not yet run on a phone.

  • All four elements work as the only clock. Measured paint rates: 60 per second from a bar with a CSS animation, 8 from the browser's own indeterminate bar, 2 from a caret (one event each 500 ms), 30 from a 30 frames per second video, and 12.5 and 4.2 from GIFs with 80 ms and 240 ms frames. A canvas with no changing element got 0 in a second.
  • Each effect stops with its element. A bar that gets a value, a field that loses focus, a paused video and a removed image raised no further paint. The page cancels nothing.
  • Drawing an element at a new place raises a second paint one frame later. Its changedElements names the element that was moved, not the clock. Before this was handled, the flag ran at twice the rate of its image and the card beat twice for each blink. Each handler now counts a tick only when changedElements holds the clock, and redraws the same frame for any other event.
  • The clock has to stay still to be told apart. When the video was drawn with a small tilt that changed each frame, 42 events a second named the video for 30 frames of film. Drawn at a fixed place it gives 30. The caret's field is a separate drawable element from the card that beats, for the same reason.
  • A clock does not have to be drawn. An image that the handler never draws raised 12.0 events a second. An image that had opacity: 0 from the start raised none, and an element with visibility: hidden has no picture. An image that was already running kept raising about 12 events a second after it was given opacity: 0.
  • A video raises one paint for each frame it shows: 46 paint events for 45 frames reported by requestVideoFrameCallback() in 1.5 s. A seek while paused raises paint for the new frame, so the scene follows the slider with no seeked listener.
  • A clock with two paint events a second gives an effect two states. Nothing raises paint between two blinks of the caret, so the heartbeat cannot ease from one state to the other without a second clock.
  • Counting events and reading the time give different effects. The flag counts, so the file's frame delay sets its speed. The loading effect reads performance.now(), so its speed is the same at 8 and at 60 events a second and only its smoothness changes.
  • Not verified: everything on a phone. In particular the caret's blink interval on Android (printed under the demo), whether the on-screen keyboard changes it, whether Chrome on Android pauses an animated image or a video's paint events when the canvas scrolls off screen, and the paint rate of a video decoded in hardware.
