A WebAssembly program whose loop waits for the paint event

A native UI program has a main loop that blocks until there is an event, and a modal dialog is a function that returns the answer. A web page cannot block. JavaScript Promise Integration (JSPI) lets a WebAssembly import return a promise while the WebAssembly code sees an ordinary blocking call. Question: can a C program draw DOM elements with drawElementImage() from a loop that blocks on the canvas paint event, and can it show a modal dialog made of real buttons from a nested blocking loop?

An edge filter on a live field: WebNN and WebAssembly

The plan for this page also asks whether a WebNN graph can run on the pixels of a live element. The button reads the pixels the program drew for the notes field and runs a Sobel edge filter on them twice: as a WebNN graph (one 3×3 convolution with two filters, then an L2 norm) and as a C function in the same WebAssembly module. After the first run the filter runs again on every frame the program draws, so typing in the field updates the picture.

Findings

  • Yes to both. run() in C is an endless loop that is called once. It draws real elements with drawElementImage(), blocks in wait_event(), and continues when the canvas fires paint. ask() blocks in the same import from a nested loop and returns 1 or 0 to its caller when a real <button> in the dialog is clicked. Measured in Chromium 157.
  • The JavaScript for JSPI is two calls. new WebAssembly.Suspending(fn) on the import and WebAssembly.promising(run) on the export. The C source has no async code, no state machine and no Asyncify build step. The module is 3 KB.
  • The loop does no work between events. With nothing happening the program draws 0 frames while the page has 30 animation frames. One change to a field gives one paint event and one frame. A focused text field gives a frame for each blink of its caret, because the browser repaints the field.
  • Drawing after the promise settles still counts as drawing in the paint event. The program continues in a microtask of the paint listener. drawElementImage() worked there in every run, and requestPaint() called from there gives another paint event.
  • The first frame has to wait for the first paint event. Before it the elements have no paint record and drawElementImage() throws. The page calls run() after the first paint.
  • A blocking loop sees one pointer state per frame. A tap can begin and end between two paint events. The page queues each pointer change and gives the program one per frame, and asks for another paint while the queue is not empty.
  • A modal dialog needs the page to say what is under it. The browser hit tests an element wherever it was last drawn and does not know the program drew a dimmed layer and a dialog over it. The page sets inert on every element the program draws as not interactive, and on the dialog while it is not drawn. In a 2D canvas that was enough: no updateElementGeometry() call was needed.
  • The module can be called while run() is suspended. The edge filter is a second export of the same module and runs on the same memory while the main loop is stopped inside wait_event().
  • The pixels of a drawn element can be read back and filtered. getImageData() on the drawable canvas returns the pixels of the notes field, and the C filter takes about 10 ms for 900×220 pixels in the test browser. Chromium logs a notice that repeated readback is faster with willReadFrequently.
  • WebNN was not measured. navigator.ml is missing from both test browsers (Chromium 153 and 157), and the plan lists it as an origin trial that needs a GPU. The graph code on this page was run only against a JavaScript stand-in for the seven WebNN calls it uses, where its output matched the C filter. Whether it builds and runs in a real WebNN implementation is unknown. The live check for it is expected to fail where navigator.ml is missing.
  • The widgets the program draws have no DOM node. The slider and the Delete button cannot be reached with the keyboard or a screen reader. The fields, the text and the dialog buttons can.
  • Not verified on a phone. Tested in headless Chromium 157 at a 2.625 device scale with touch events: tapping, typing, dragging the slider and both dialog buttons. If the canvas loses its drawing context the page shows a message, and the program draws again when the context is restored.
