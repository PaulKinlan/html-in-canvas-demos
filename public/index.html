What happens when the DOM can go anywhere a pixel can?

The HTML-in-canvas API lets a <canvas> draw DOM elements. The drawn elements keep working: they take clicks and typing, their text can be selected, and they stay in the accessibility tree. This site is a set of experiments that test what the API can and cannot do. Each experiment page states the question it asks, runs checks in your browser and lists its findings. There is also a one-page tutorial for the API.

Experiments

Each page asks one question about the API and reports what worked and what did not. Some build a custom element or a library to answer it. The code is on each page. The accessibility audit and the performance test measure the claims made on the other pages.

Examples

Fifteen of the experiments, with pictures. In each one, the content in the picture is DOM drawn by a canvas, and it accepts input.

One element streamed to a phone

Scan a code and one panel of the page is on your phone over WebRTC. Taps and typing on the phone are sent back and applied to the element.

Widgets moved into another window

Pull a widget into a popup, an always-on-top window, another tab or another origin. What you do there happens to the element on this page.

Record and replay DOM frames

A ring buffer of frames of an element. Drag the slider to see earlier frames, replay the last five seconds, or restore an earlier state with its form values.

Picture-in-picture for any element

pipElement(el) puts an element in a window above your other windows: moved there, as a live picture that takes input, or as a video.

Share one panel, not the screen

Send one panel of a page to a support agent or a vision model. Fields marked private are blacked out before the frame is sent, and actions need approval.

Export an element as PNG or video

captureElement(el) wraps an element in a canvas for one frame and returns a PNG. The same library records video and prints.

A form in a three.js scene

A form used as a texture on a laptop screen, a billboard and a curved wall. Typing, Tab and text selection work on all three.

Fragment shaders on elements

fx="ripple" draws an element through a fragment shader. CSS custom properties set the uniforms, and you can supply your own GLSL.

Transitions between two live states

Shatter, fold and burn transitions drawn in WebGL. Both states accept input during the transition, and it can be held part way.

A magnifier over live DOM

Fifteen lenses. The area under the lens is drawn again at the lens zoom, so 4px text is sharp, and clicks and typing pass through.

Forms on a simulated mesh

Forms drawn on jelly, cloth and paper meshes. Hit testing follows the mesh, so a click reaches the control under the pointer.

Text drawn glyph by glyph

Each letter of a paragraph is a particle. The paragraph is still one element, so selection, find-in-page, links and editing work.

A zoomable board of documents

Each tile is an element or a same-origin iframe drawn under a zoom transform. Text is rasterised again at each zoom level, up to 800%.

Cross-origin widgets without an iframe box

A price and a product card from another origin, laid out inline in a blog post. The other origin asks the reader before it sends any pixels.

HTML panels in WebXR

HTML panels in a three.js XR scene. Controller rays become pointer events on the elements. Includes a desktop preview and a headset emulator.

A select whose picker is drawn by a canvas

The options of a customisable <select> are moved into a canvas inside its picker and drawn as a wheel, a fisheye list, a radial menu, a 3D carousel, a hand of cards or a helix. The select keeps the value and the keyboard.

Date, time and colour pickers made of buttons in a canvas

A clock, a calendar and a ring of swatches replace the built-in pickers of three ordinary inputs. Every hour and day is a real button that the canvas moves and fades.

A datalist whose suggestions are drawn by a canvas

The <datalist> of a text input is moved into a canvas in a popover. Its options are drawn as a list or as pills and rearrange while you type.

The building block

canvas-slot.js is one dependency-free module. Children with a slot name are projected into a canvas; you get a render callback with a draw(name, x, y) helper. Add worker="…" to render off the main thread, or pair it with slot-share.js to publish slots to other tabs and origins. 

<script type="module" src="https://html-in-canvas-demos.kinlan-test.workers.dev/lib/canvas-slot.js"></script>

<canvas-slot id="stage">
  <h2 slot="title">Real DOM</h2>
  <button slot="cta">Still clickable</button>
</canvas-slot>

<script type="module">
  const stage = document.getElementById('stage');   // the <canvas-slot> element

  // draw(slotName, x, y) is drawElementImage() for the element in that slot.
  stage.onrender = ({ ctx, draw, time }) => {
    ctx.rotate(Math.sin(time / 800) * 0.05);
    draw('title', 20, 20);
    draw('cta', 20, 90);
  };
</script>

Limits of the API

Four limits shaped most of the code on this site. The tests behind each are in FINDINGS.md.

  • The element must be a descendant of the canvas. There is no way to draw an element by reference. The slot demos use a shadow root to work around this.
  • An element has one hit-test region. If it is drawn twice, or in pieces, only one position receives input. The portal, lens and transition demos move the region to the pointer.
  • An ElementImage draws only into its source canvas. To show an element in another document, the demos send pixels and forward input events back.
  • An element that is not drawn can still take focus. Tab reaches controls that are not visible unless the page marks them inert.
