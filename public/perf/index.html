Performance wall: how much live DOM can a canvas carry?

Each row keeps adding live elements, all moving every frame, until the frame rate falls off. The same scene is run as plain DOM with CSS transforms, as a 2D canvas drawing every element with drawElementImage, and as a worker drawing transferred ElementImage snapshots. The numbers are from this device, right now.

Cells are frames per second with that many elements (for worker rows: the worker's frame rate, which is what moves on screen). The wall is the largest count that held 90% of this display's refresh rate. A row stops at the first count under half the refresh rate.

What the rows mean

  • Plain DOM is the baseline: the same cards, absolutely positioned, moved with transform. The compositor does the work.
  • 2D canvas asks for a paint event every frame and redraws every element. The cost is one drawElementImage replay per element per frame, on the main thread.
  • 2D canvas, changing content also rewrites the text of some elements each frame, so their paint records are rebuilt.
  • Worker transfers the canvas to a worker. The main thread only captures an ElementImage when an element changes; the worker redraws every frame from the snapshots it holds.
  • Busy main thread adds 40ms of blocking script to every main-thread frame. Canvas drawing on the main thread drops to that rate; the worker does not.
