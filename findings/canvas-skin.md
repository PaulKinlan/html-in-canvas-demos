# Per-element themes (`/canvas-skin/`, `lib/canvas-skin.js`, `lib/canvas-skin-themes.js`)

Measured in headless Chromium 157 (C157) on 2026-11-22, at 412 px wide, device scale 2 and 2.625, with taps sent as touch events. Not run on a phone.

`<canvas-skin>` wraps one element in a small drawable 2D canvas. A `skin` attribute on an ancestor chooses how every wrapper under it draws. 29 skins are built in: glass, pencil, gel, terminal, blueprint, thermal camera, neon sign, embroidery, Christmas, seaside, LED board, punch card, oscilloscope, X-ray, 1-bit, ASCII, comic, 3D blocks, stained glass, clay, brushed metal (aluminium, steel, brass, copper, chrome), underwater, gravity, holographic foil, screen print, crayon, impressionist, old master and native (the browser's own drawing).

| Question | Result | Reason or detail |
|---|---|---|
| Can a page be themed with one drawable canvas per element instead of one canvas for the page? | Yes (measured). 53 wrappers on the page, 32 of them in the form. | Shadow root: `<canvas content="drawable" layoutsubtree><div drawable><slot></slot></div></canvas>`. The element is slotted and stays in the page's DOM. |
| Do the wrapped controls take input? | Yes (measured). Tap on a checkbox, click on a range, label click, typing, form data. | The canvas has `pointer-events: none`, the drawable `<div>` has `pointer-events: auto`. `elementFromPoint()` at a button's centre returns the button. |
| Does the canvas's extra 14 px on each side take hits from neighbours? | No (measured). | A point 6 px outside a wrapped button, over its canvas, returned the element under the canvas. |
| Can a skin draw a control from its state without painting the native control? | Yes (measured) for checkbox, radio, switch, range, progress. | The native control is drawn once per paint inside an empty clip. It toggled on `click()` and on a tap, and a click at 80% of a range set 82. |
| Is a block `<div>` inside `<canvas layoutsubtree>` as wide as the canvas? | No (measured). It is as wide as its content: a heading was 211 px in a 380 px canvas. | It needs `width: calc(100% - 28px)`. |
| Does a wrapper inside a wrapper draw and take input? | Yes (measured in C157). | The outer canvas had the inner button's pixels, and the point found the `<button>`. `/nested-frames/` has a report of nested canvases not drawing on A159. |
| Can the wrappers share one WebGL context? | Not to draw elements (inferred from `findings/` results on `ElementImage` and `texElementSubImage2D()`: an element is drawn only by a canvas it is inside). Yes for pixels that are not an element (measured, headless Chromium 157, 2026-11-22). | The elements are drawn by 2D canvases, with SVG filters used as `ctx.filter = 'url(#id)'` in each wrapper's shadow root. The glass skin uses one WebGL2 context on a detached canvas (`lib/glass-gl.js`): each glass element sends the part of the background copy that lies behind it as a texture, the shader runs, and the wrapper copies the result with `drawImage()`. |
| Can a glass skin show the page background through an element? | Yes, when the background is known to the skin (the live check "The glass shader bends the background" compares refractive index 1.5 with 1). | The canvas cannot read what is behind it. The skin has the root's CSS gradients and diagonal lines again as canvas calls and draws them into a shared plain canvas. The shader treats the element as a slab with a rounded rim: signed distance to the rounded rectangle, surface height and normal, `refract()` once each for red, green and blue, an 8-tap blur for frost, highlights from a light direction. Settings: light angle, rim width, thickness, refractive index, dispersion, frost, highlights, tint. Five modes are sets of these values (Regular, Clear, Frosted, Thick lens, Prism); the values are this page's, not Apple's. Without WebGL, or after the shared context is lost, glass is drawn in 2D as 12 enlarged rings. No check exercises the 2D version after a real loss. |
| How is a change of skin animated? | Each wrapper copies its canvas with `drawImage()` into a plain canvas, switches, and fades the copy out over the new drawing in 640 ms (measured: order 10, 130, 323 ms for three buttons at 0.3 px per ms). | `CanvasSkin.apply(root, name, { x, y })` gives each wrapper a delay by distance from the point. The root's old background stays on a layer whose mask has a growing hole. |
| What does it cost? | 18.8 MB for all canvases by the guard's estimate at scale 2.625 (`npm run check:jank`, 2026-11-22), largest canvas 0.67 MP, 1 WebGL context. 30 wrapped buttons: 99 KB each at scale 2 (measured). | Wrappers more than one screen away set their canvas to 0 by 0. The WebGL context is made when the first glass element paints, which is at load on this page because it opens in glass. |
| What happens after a lost context? | The wrapper moves the element out of the canvas and sets `plain` (measured with a dispatched `contextlost` event). | The element then has the skin's font and colours and a CSS border. |

## Things that bit

- A block wrapper has no intrinsic width, because its only in-flow content is the box that holds the canvas. In a flex row or a grid cell with `justify-items: start` it was 0 px wide and got no paint event. Wrappers of buttons, checkboxes, radios, switches, labels and outputs are inline and are sized from the element.
- Glass background: a CSS gradient tile cuts each blob at the tile's edge. The seam showed in the page and in the canvas copy until each blob was listed three times, one tile apart.
- `ResizeObserver` on the canvas as well as on its child would report a loop error, because the canvas is the child's ancestor. The wrapper observes the child only and computes the canvas size from it.
- Reported from A159 on 2026-11-22, three times in one visit: "ResizeObserver loop completed with undelivered notifications". The wrapper wrote its box size inside the observer callback, which resizes other observed elements (the outer wrapper of a nested pair, a neighbour in a flex row). The sizes are now read and written in one animation frame for all wrappers. The error did not occur in C157 before or after, so the fix is not verified.
- Playwright's `setViewportSize()` resets a forced device scale factor to 1.

## Skins added on 2026-11-22 (headless Chromium 157)

| Question | Answer | How |
|---|---|---|
| Can a skin work on the pixels of the element's picture? | Yes (seen in screenshots, no live check yet). | `grab()` in `lib/canvas-skin-draw.js`: the wrapper's canvas draws the element, the whole canvas is copied into a plain canvas with `drawImage()`, and the wrapper's canvas is cleared. The embroidery skin draws that copy small and enlarges it with no smoothing, then uses a repeated cross as a `destination-in` mask. The sea skin gives the copy to a shader as a texture. |
| Can other shaders use the glass skin's WebGL context? | Yes. `check:jank` counts 1 WebGL context with glass, metal, sea and space all on the page. | `shade(name, body, panel, scale, values, source, copy)` in `lib/glass-gl.js` compiles a program per name in the same context. Each call is one pass into the shared canvas and one `drawImage()` into the wrapper. |
| Can a skin animate without painting every frame? | Yes. | A skin sets `frame.wait` to a number of milliseconds and the wrapper asks for its next paint after that time. The sea skin uses 50 ms. |
| Can a skin use where the page was touched? | Yes (seen in screenshots after synthetic pointer events, no live check yet). | The thermal skin listens for `pointerdown` and `pointermove` on the document, keeps the last 40 points for 4.5 seconds, and asks the wrapper under the pointer to paint. |

| Can an element be drawn bent by the elements round it? | Yes, inside its own canvas (seen in screenshots). | The gravity skin measures every wrapper at most once in 0.8 s, gives each a mass from its size, and gives the shader the four that pull hardest on this element and the pointer. A wrapper cannot draw outside its canvas, so the displacement is capped at 13 px (the canvas has 14 px of room). The page background is CSS and is not bent. |
| Does a sensor reach a skin? | Written, not verified: headless Chromium sends no `deviceorientation`. With a mouse the same code follows the pointer. | Foil and metal move their highlight with tilt. The wrappers are painted again at most 12 times a second and only when the tilt changed by more than 0.02. |
| Does the shader need the element's picture each frame? | No. | `shade()` keeps one texture per element when given `keep` and `sig`. The underwater skin skips the 2D drawing, the copy and the upload while only the water moves. |

Owner's notes from the phone, 2026-11-22 (Chrome 159, Android): the first underwater skin was "pretty slow". It drew, copied and uploaded every near wrapper 20 times a second. It now uploads only on change, paints 15 times a second on screen and 2 off it. Not measured again on the phone. The first space skin (a ring of bent stars round each box over tiled dot stars) and the first metal skin (chrome with a horizon) were not liked, and were replaced by gravity and brushed metal.

Problems met: LED lamps 3 px apart made 16 px text unreadable, and 2 px apart reads as a dot-matrix sign. Dark lettering over the lead lines of the stained glass was unreadable until an SVG filter put a pale ground round each letter. A grain of 0.6 on the metal normal made the reflection unreadable noise and hid the field text; 0.07 reads as brushing. A cross-stitched heading at 2.2 px cells was not legible, so only pictures are cross-stitched and text is drawn through a lighting filter.

## Third round, 2026-11-22 (headless Chromium 157)

The owner reported from the phone (Chrome 159, Android) that the change of skin had become "really slow", that the oscilloscope showed no difference between states, that old master "didn't really work", that stained glass was "really hard to see anything in" and that clay was not exciting. `npm run reports -- --since 3h --list --page /canvas-skin/` at 11:17 showed nine "ResizeObserver loop completed with undelivered notifications" errors from three visits, 66 to 69 minutes old, and no lost context, crash or shader report.

| Question | Answer | How |
|---|---|---|
| Can the wrappers limit how much they paint in one frame? | Yes. With the CPU slowed 4 times at device scale 2.625, a change to the stained glass skin went from 6 frames in 2.4 s to 46, old master from 7 to 33, screen print from 6 to 55, pencil from 8 to 45 (`perf.mjs`, a scratch script that counts `requestAnimationFrame` gaps after a click). These are software-rendered numbers and say nothing about the phone. | `ask()` and `run()` in `lib/canvas-skin.js`. Paints that follow a paint are asked for by one loop. Each frame it asks the wrappers that waited longest until their last paints' script time adds up to a budget (6 ms at first). A late frame multiplies the budget by 0.7 (not below 1.5 ms) and a frame on time by 1.06 (not above 8 ms). Entrances are timed by the clock, so a wrapper that waits skips ahead. |
| Can a wrapper decline a paint event the browser raises? | Yes. A paint handler that returns without drawing leaves the canvas with the picture it had. | A change of skin changes the CSS of every wrapper, so the browser raises `paint` for all of them in one frame. When that frame's paints have already taken twice the budget, the handler returns and joins the loop. It never declines the first paint or a paint after the canvas was resized, which would show an empty canvas. |
| Which wrappers animate? | Only those in the window. | `apply()` reads each wrapper's box. A wrapper outside the window (but within one screen, so it has a canvas) changes at once with no copy of its old picture and no entrance. |
| What did the old root background cost? | The first change away from the glass skin had one gap of about 700 ms in the slowed test browser, with or without the mask. It is the raster of a second layer with the glass background, not script (the long animation frame had under 80 ms of script). Not measured on a phone GPU. | The layer with the old background had a `mask-image` whose radius was an animated registered property. It is now two layers: the old background, cut with `clip-path: inset()` to the part in the window, and the new one with an animated `clip-path: circle()`. The soft 70 px edge of the mask is gone. |
| What does the page report about a change? | Frames drawn and missed, the longest gap, the number and script time of element paints, paints put off, the budget, the `event` timing entry of the tap and the `long-animation-frame` entries. | `measure()` in `public/canvas-skin/page.js`. The same numbers go to the report endpoint as type `skin-change`, so `npm run reports -- --page /canvas-skin/` shows what the phone measured. |
| Can a skin have options? | Yes. Live check "CanvasSkin.set() changes an option of a skin". | A skin gives `settings`, `options` (numbers with a range, or choices), optional `presets`, and `vars(settings)` for CSS custom properties. `CanvasSkin.set(name, values)` writes them and repaints that skin's wrappers. The page builds one panel from the list. 15 skins have options. |
| Can an SVG filter in the wrapper's shadow tree read a CSS variable of the skin? | Yes: `<feFlood style="flood-color: var(--beam)">` followed the oscilloscope's beam colour (seen in a screenshot). `flood-color="var(--beam)"` as an attribute does not. | The variable is set on the wrapper by the skin's rule and inherits into the shadow tree. |
| Can a picture be turned into characters without reading pixels each paint? | Yes. | The ASCII skin draws the element's picture into a plain canvas with one pixel per character, made with `willReadFrequently`, reads it once and keeps the rows of characters until the picture's size or source changes. `check:gfx` allows the read with a `gfx-allow` comment. |
| Can a 2D canvas draw an element as a block in perspective that follows scrolling? | Yes (seen in screenshots at two scroll positions). | The 3D blocks skin keeps the face at the layout position and draws the back and two sides toward the middle of the window. A `scroll` listener asks every wrapper in that skin to paint through the frame budget. |

First numbers from the phone (Chrome 159, Android, device scale 3, 83 wrappers, 2026-11-22 11:46, `skin-change` reports): LED board to oscilloscope 97 frames drawn and 3 missed in 1.6 s; terminal to LED board 79 drawn, 26 missed, longest gap 50 ms; glass to gravity 56 drawn, 31 missed, longest gap 117 ms, 272 ms of paint script; gravity to ASCII longest gap 150 ms and 456 ms from the tap to the next frame, with 14 long animation frames of at most 68 ms. Two of the four ended with the budget at its floor of 1.5 ms although paint script was 82 and 100 ms in all: the loop took the shortest gap between two callbacks as the screen's frame time, so ordinary 60 Hz frames counted as late. It now uses the middle of the last 15 gaps, as the nearest common rate. Not measured again on the phone.

More from the phone at 11:52 (same device, after the frame time fix): X-ray to thermal and thermal to punch card missed 0 of 94 and 91 frames; 1-bit to comic missed 4 of 89; glass to X-ray 17 of 94; comic to 1-bit 25 of 93; browser default to gravity 28 of 94 with 164 ms of paint script. The owner called gravity "particularly slow". While a finger moved, every gravity wrapper within 300 px drew its shapes, copied its canvas and uploaded a texture on each frame. The gravity skin now keeps one texture per element as the underwater skin does, asks for those paints through the frame budget, and reaches 190 px. In the test browser 40 pointer moves cost 4.9 ms of script per element paint, 10.1 ms before (software WebGL, device scale 2). Not measured on the phone.

What changed in the skins: the oscilloscope's shapes are lists of points, the element with focus (`:focus`, so also after a tap) has a point with a fading tail running along them, a pressed element is traced twice, and a field becomes a whole box with focus. Old master uses a Kuwahara filter, lit brush ridges, a lamp that also lights the wall through two CSS variables written on the root, and gilded frames drawn after the shader. Stained glass elements are a pale pane with a border of coloured pieces, so text is dark on pale glass. Clay presses the text of a button or field into the surface (the element's picture is the stamp).

## Not verified

- Everything on Chrome 159 for Android: how many small 2D canvases it keeps, the speed of a change of skin with about 20 wrappers fading at once, the pencil skin's SVG displacement filter on every wrapper, the native picker of a wrapped `<select>`, the on-screen keyboard over a wrapped field, a screen reader. Opening `/canvas-skin/` on the phone, changing skins and running the checks would verify these. The line under the form reports how many wrappers fell back to plain HTML and why.
- Frame rate. The test browser renders in software.
- The frame budget on the phone. The numbers above come from a software renderer with the CPU slowed. The line that begins "Change from" under the form, and the `skin-change` reports, are the phone's own numbers after the next visit.
- Whether an animated `clip-path: circle()` on a full-size layer is cheaper than the animated mask on the phone.
- Tilt for the 3D blocks skin (no `deviceorientation` in the test browser), the speed of repainting every block while scrolling, and the look of the ASCII skin with the phone's monospace font.
- The beam running round a focused element after a touch tap on the phone. In the test browser `tap()` on a field showed it.
- The sea skin on the phone: every near wrapper does a canvas copy, a texture upload, a shader pass and a `drawImage()` 20 times a second. If the phone cannot keep up, raise `frame.wait` or animate only the element under the pointer.
- The no-WebGL versions of metal, sea and space. They are written and no check runs them.
- The glass shader on a phone GPU: the cost of one texture upload and one shader pass per glass element per paint, and how dragging a glass slider (every glass element repaints per input event) feels. The line under the form says whether glass is drawn by the shader or the 2D version, and why.
- A WebGPU version of the glass shader. The project order is WebGPU, WebGL, 2D; only WebGL and 2D are written.
- The "ResizeObserver loop" error reported from the phone on 2026-11-22. Sizes are now applied in one animation frame; the error did not occur in Chromium 157 before or after, so the fix is not confirmed.
- `computedRole` was not available in the test browser, so the role check reports only form and label behaviour there.

## For the index

- Custom elements and slots: a drawable `<div>` round a `<slot>` in a per-element canvas, with `pointer-events: none` on the canvas, leaves the slotted control hit-testable and keeps the canvas's margin from taking hits.
- Layout: a block child of `<canvas layoutsubtree>` shrinks to its content unless given a width.
- Forms: a control drawn only in an empty clip (never painted) still takes taps and drags.

## Open ideas

- A skin whose background moves (the glass background drifting) would need every glass wrapper to repaint per frame.
- A wrapper could take `backdrop` from a second canvas that draws the root, to show arbitrary content through glass.
- `CanvasSkin.wrap()` could run again from a `MutationObserver` for elements added later.
