# New platform features and HTML-in-canvas: a plan

This document lists every feature that chromestatus.com records for Chrome 130 to 160, says where each one could be combined with the HTML-in-canvas API (`<canvas content="drawable">`, `drawElementImage()`, `texElementSubImage2D()`, `GPUQueue.drawElementImageToTexture()`), and plans demos from the combinations.

The same content is on the site at [/chrome-apis/](https://html-in-canvas.page/chrome-apis/), with filters. This file is generated: edit `tools/chrome-apis/ideas.json` and `tools/chrome-apis/demos.json`, then run `npm run build:plan`.

## Method

- Source: `https://chromestatus.com/api/v0/features?milestone=N` for N = 130 to 160, fetched 2026-11-21. Chrome 159 is stable and 160 is beta on that date.
- 678 features: 597 enabled by default or rolling out, 56 in an origin trial or developer trial, 25 deprecated or removed.
- 359 features have an idea below. 68 are rated 3 (the feature changes what a canvas draws, or gives a drawn element a new input or output), the rest 2 (useful in a demo) or 1 (a small note).
- "Measured" means a probe on [/chrome-apis/probes.html](https://html-in-canvas.page/chrome-apis/probes.html) drew an element with the feature and read the result back. 44 features have a probe. Everything else is inferred from the feature's description.
- Probes ran in two headless Chromium builds: Chromium 157, headless shell; and Chromium 153, full browser with the canvas-draw-element flag. The phone used for testing this site runs Chrome 159, which neither build matches exactly.

## Planned demos

Ranked. Each demo lists what it shows, how it would be built, what was measured, what is uncertain and the features it uses.

### Build next

These run in Chrome 157 to 159 today, and most have a measured result behind them.

#### 1. Streamed HTML that the canvas draws as it arrives

- **Shows:** Markup streamed into a drawable element with streamAppendHTML(), from the Prompt API or from a fetch. The paint event's changedElements names each new block, and the canvas draws new blocks through an effect (noise that resolves into the text, a scan line, ink that spreads) while older blocks are already plain and selectable.
- **Build:** One drawable article element. A WritableStream from streamAppendHTML() takes chunks from LanguageModel.promptStreaming() where the model is on the device, and from a Workers AI endpoint otherwise. A per-block age map drives one uniform per block. A second mode uses out-of-order streaming: the server sends a page skeleton, then fills sections in a different order, and each section arrives with its own effect.
- **Measured:** streamAppendHTML() raised one paint event per chunk with no requestPaint() in Chromium 157.
- **Uncertain:** Whether changedElements lists the new block or only the container. Whether the Prompt API model is downloadable on the test phone (the test browser reports downloadable for LanguageModel and Summarizer but cannot fetch a model). Streaming methods are missing in Chromium 153, so the page needs a fallback that appends with setHTML().
- **Needs:** A device with the on-device model for the Prompt API path. The fetch path runs anywhere.
- **Builds on:** [/shader-css/](https://html-in-canvas.page/shader-css/), [/support/](https://html-in-canvas.page/support/)

#### 2. A CSS-only carousel drawn as a cover flow

- **Shows:** A scroller with scroll snap, ::scroll-marker and ::scroll-button(), written with no script, drawn by a canvas as a ring of tilted cards. The native markers and buttons are drawn where the scene wants them and still scroll the real list. Keyboard, touch fling and the accessibility tree are the scroller's own.
- **Build:** Each slide is a drawable child, drawn with a perspective transform taken from its offset to the scroll position. sibling-index() gives each slide its slot on the ring. A scroll-state(snapped) query sets a custom property on the snapped slide, which the canvas reads as the focus uniform. A second layout draws multicol ::column fragments as book pages with a page-turn shader.
- **Measured:** Marker and button pseudo-elements are in the element picture, and a real click on a drawn marker scrolled the list (Chromium 153 and 157). A scroll-state(stuck) query restyled a drawn element and raised a paint event by itself.
- **Uncertain:** Whether markers can be drawn apart from their scroller: they are part of the scroller's picture, so moving them means drawing the scroller twice with different clips. Touch fling on a scroller whose slides are drawn away from their layout boxes.
- **Builds on:** [/three-form/](https://html-in-canvas.page/three-form/), [/portal/](https://html-in-canvas.page/portal/)

#### 3. Native popovers, hints and commands on warped surfaces

#### 4. HDR interface: elements brighter than white

- **Shows:** Ordinary DOM drawn into a float16 canvas, with chosen pixels raised above standard white on an HDR screen: a primary button that emits light, a focus ring that blooms, a notification badge at 4 times white. dynamic-range-limit keeps body text at standard brightness.
- **Build:** A 2D context with colorType 'float16', colorSpace 'display-p3' and, in Chrome 160, toneMapping 'extended'. Draw the element, then composite it again with 'lighter' through a mask made from a CSS custom property (--glow). A WebGPU path uses an rgba16float canvas with toneMapping extended and a bloom pass. A slider sets the headroom. A dynamic-range media query shows a notice on a standard screen.
- **Measured:** In a float16 Display P3 canvas, color(display-p3 1 0 0) on a drawn element read back as 1, 0, 0 and color(srgb-linear 4 4 4) read back as 1.82, so values above 1.0 survive drawElementImage() (Chromium 153 and 157).
- **Uncertain:** Whether values above 1.0 reach the screen from a 2D canvas before Chrome 160. Whether texElementSubImage2D() and drawElementImageToTexture() keep them in a 16-bit float texture. Why 4.0 read back as 1.82 (a tone curve or a limit).
- **Needs:** An HDR screen. Most recent Android phones have one.
